# 振宇五金壘球記分 App

手機版壘球攻守即時記錄：打線編排、即時攻守紀錄、換人與戰績統計。原本以 Claude Artifact 形式運作，現已支援免登入部署（Supabase 資料庫＋GitHub Pages 靜態網頁），球隊成員不需要 Claude 帳號即可使用。

Live artifact: https://claude.ai/code/artifact/733c6672-f0b4-4d85-8e8b-48e776394032

## 使用說明

這份文件記錄「數據分析」與「出席與排行榜」頁面中，各卡片原本顯示在畫面上的說明文字。這些說明已從 App 畫面移除（讓卡片更精簡、橫向閱覽時也更好排版），改記錄在這裡供查閱。

### 數據分析頁面

#### 球隊戰績
- 用本 App 記錄的比賽（含聯賽／盃賽／季後賽，依卡片內的球季／賽事類別篩選）計算實際勝負與對戰明細；「球季」預設為目前現場在打的球季，可切換到「全部賽季」看所有球季合計。
- 「球季積分表」是當時球隊試算表或紙本積分表匯入的全組戰績，只有總積分／排名／各隊逐場勝和敗序列，沒有記錄每場對到哪一隊，所以無法像上面一樣列出對戰對手明細；「戰績」欄若顯示「（無逐場資料）」代表來源只留下最終總分，沒有逐場序列。
- 盃賽、季後賽的比賽單獨統計於「盃賽／季後賽打擊成績」，不會計入下方球員成績查詢的球季／生涯數據。

#### 其他球隊之間的比賽結果登錄（Version 45）

「球隊戰績」卡片裡的「📋 登錄其他球隊比分」按鈕，用來輸入跟本隊（振宇五金）無關、其他球隊互相對戰的比分——本隊自己的比賽不用在這裡輸入，App 記錄的比賽會自動算入戰績。

- 點按鈕後會開啟一個輸入視窗，一次最多可以填 7 組對戰紀錄（球隊A、比分、比分、球隊B、日期），空白的列會自動略過，不會被當成錯誤。
- 新增的紀錄會歸入目前「球隊戰績」卡片上方選擇的球季／賽事類別（可以先切換好球季/賽事類別篩選再點開登錄視窗）。
- 視窗內也會列出目前這個球季/賽事類別範圍內已經登錄過的紀錄，可以個別刪除。
- 登錄或刪除都需要輸入管理密碼（Supabase 部署模式才會出現這個檢查，Claude Artifact 模式不受影響）——因為輸入錯誤會影響全隊看到的排名，跟編輯已完賽比賽記錄一樣的保護機制。
- 只要任何球季/賽事類別範圍內有登錄過至少一筆其他球隊的比分，「球隊戰績」卡片就會自動顯示完整的多隊排名表（排名／球隊／出賽數／勝-和-敗／勝率／積分），把本隊自己的比賽（App 自動算）跟這裡登錄的其他球隊比分合併計算；如果完全沒有登錄任何其他球隊的比分，就會維持顯示本隊單一列的戰績（不會秀出不完整、誤導性的排名表）。

#### 球員成績查詢
- 選擇球員可查看該球員累積至今的生涯數據（含尚無出賽紀錄的球員）；「球季」可切換只看單一球季，或所有球季合計的生涯總和。
- 2025、2025-2026聯賽的數字含由球隊試算表匯入的歷史成績；每個球季會自動併入用本 App 記錄且標記為該球季的比賽。
- 盃賽／季後賽的比賽不計入任何球季或生涯數據，另見「球隊戰績」卡片內的盃賽／季後賽打擊成績。
- 選「全部」則顯示這個球季（或生涯）所有球員的成績一覽，以及全隊擊球落點總覽。
- 落點圖僅根據用本 App 記錄的比賽計算，試算表匯入的歷史成績無落點資料，舊比賽若未記錄落點也不會計入。顏色越紅代表該項數值越高，越藍代表越低；灰色代表該落點尚無資料。

#### 投手成績查詢
- 選擇投手可查看累積至今的投球數據（含尚未登板的球員）；「球季」可切換只看單一球季，或所有球季合計的生涯總和。
- 三振／保送／失分／局數完全來自本 App 記錄的比賽；勝投／出賽則是本 App 記錄比賽的累計，另外「2025」與「2025-2026聯賽」兩個球季都併入由球隊試算表匯入的歷史勝投／出賽。盃賽／季後賽不計入。

#### 對手分析
- 選特定對手／背號時，下方僅顯示該球員的紀錄；不同隊伍可能有相同背號，已依隊伍區分，不會混合成同一人。
- 落點圖顏色越紅代表該項數值越高，越藍代表越低；灰色代表該落點尚無資料。

### 出席與排行榜頁面

- 出席率、排行榜都可切換只看單一球季或生涯總和；選特定球季時，名單只列出當季確實在隊上的球員（依匯入的球季試算表或當季比賽紀錄判斷），不會列出還沒加入球隊的人。排行榜與球員成績查詢一致，只計入聯賽成績，不含盃賽／季後賽。
- **排行榜**：打擊類項目僅列入打席數達「總場數 × 60%」以上的球員（比照「有效打席」門檻排除，避免出賽場次太少的球員因為樣本太小佔據排行榜前段）；勝投是投手單項統計，不受此門檻限制。
- **出席率**：以目前累積（或選定球季）的場數（含進行中、盃賽／季後賽）計算，出席＝曾列入打線或替補名單。


## 開發紀錄

### 資料模型重點
- `games`（進行中比賽，任何人可寫）與 `games_final`（已完賽，僅管理員可改／刪）兩個集合。
- 比賽文件欄位：`lineup`、`bench`、`oppRoster`、`oppBattingSlots`（見下方 Version 15）、`battingIdx`/`oppBattingIdx`、`plays[]`（每筆含 `side:"us"|"opp"`、`code`、`batterNumber`、`batterName`、`zone`、`battedType`、`half`、`inning`）、`statOverrides`、`status`（setup|live|final）、`season`、`competitionType`（見下方 Version 12）。
- `oppLogOnly:true`：標記「從球隊試算表匯入的歷史對手打席彙整」（非我方實際出賽的單場比賽）。會被首頁比賽列表、出席率統計排除，但仍會計入對手分析（落點／結果／球種／背號分析）。
- **對手背號跨隊重複**：不同對手球隊可能有相同背號但是不同人（背號不是全域唯一的），所以對手分析中所有依背號分組/篩選的地方都必須用「隊名＋背號」組成的複合鍵（`computeOpponentBatting` 內部用 `team+"||"+number`，`oppRowKey(r)` 產生同樣的鍵），不能只用背號本身，否則不同隊的同背號球員資料會被誤merge在一起。這個複合鍵規則現在也用在紀錄頁面（見下方 Version 11）。
- **球隊自己的歷史球季資料**：`team/season_2025`、`team/season_2025_2026` 兩份 db 文件（各為 `{rows:[...], updatedAt}`），存放從球隊試算表匯入的「本隊」球員球季彙總數據（背號、姓名、PA/AB/H/1B/2B/3B/HR/BB/SF/RBI/K/DP/E，無得分R欄位，試算表本身未提供）。透過 `Store.getSeasonStats(key)` 讀取（`db` 不可用時 fallback 到 localStorage `sb_<key>_v1`）。**⚠️ Version 20／22 更新**：個別球員物件現在可能額外帶有 `W`（勝投）／`G`（出賽）欄位（`season_2025` 與 `season_2025_2026` 兩份文件的部分球員都有，見下方 Version 20、Version 22）；另外背號重複的已離隊球員（目前是 `season_2025`／`season_2025_2026` 裡的王崇綺、曾筱茹）`number` 欄位已加註 `(原)` 後綴（例如 `"19(原)"`），跟現役同背號球員（鍾嘉文、謝文隆）的資料分開，見下方「背號重複的已離隊球員與生涯數據分離」條目與 Version 20。**⚠️ Version 23 更新**：個別球員物件現在還可能額外帶有 `GP`（出賽次數／出席場次，跟 `G`＝登板次數是不同欄位，刻意取不同名字避免衝突）欄位，供出席率統計使用，見下方「歷史球季的出席率資料」條目與 Version 23。
- **落點分析的每格細節（Version 11 新增）**：`computeZoneAnalysis()` 除了原本的 `zoneCounts`（每格次數）外，現在也回傳 `zoneStats`（每格 `{count, AB, H, TB}`），供打擊率／長打率兩種落點指標計算用。AB 認定規則與 `computeOpponentBatting` 一致：除 BB、SF 外都算打數（含 FC／失誤／三振／出局）。
- **比賽的球季與賽事類別（Version 12 新增）**：每場比賽文件新增 `season`（自由文字，供分季查詢用）與 `competitionType`（`聯賽`｜`盃賽`｜`季後賽`，預設 `聯賽`）兩個欄位，建立比賽時在「新比賽設定」頁可填，事後也可在「編輯紀錄」內修正。只有 `聯賽` 類的比賽會計入球季／生涯數據；`盃賽`／`季後賽` 另外歸類、彼此不混。沒有 `season` 欄位的舊比賽（此功能上線前記錄的）一律 fallback 視為 `"2025-2026聯賽"`（沿用當時 App 的預設假設）；沒有 `competitionType` 的舊比賽視為 `聯賽`。輔助函式：`gameSeason(g)`、`isLeagueGame(g)`（都定義在 `computeZoneAnalysis` 附近的「Season-wide aggregation」區塊）。**⚠️ 這個 fallback 只該用來兜底「Version 12 上線前」真正的舊資料**——如果之後又有比賽文件因為別的原因（例如手動寫入 db、或建立流程被跳過）缺了 `season` 欄位，也會被同一個 fallback 靜默歸類到「2025-2026聯賽」，造成「明明是新比賽卻算到上一季戰績」的錯誤（見下方 Version 17 的實際案例）。建議定期用 `read_db`／`db_op:"list"` 檢查 `games_final`（排除 `oppLogOnly:true` 的匯入資料）有沒有缺 `season` 或 `competitionType` 的文件。
- **出席率／排行榜的球季篩選與名單排除（Version 13 新增）**：出席率頁面新增「球季」下拉（生涯／各球季，與球員生涯查詢共用 `seasonOptionsFor()` 產生選項），選特定球季時改用 `rosterForSeason(seasonKey, games)` 決定要列出的球員名單，而不是永遠用完整的 `AppState.roster`——判斷依據是「該球員的背號有沒有出現在當季匯入的試算表資料（`SEASON_IMPORT_KEYS` 對應的資料）裡，或有沒有出現在任一場標記為該球季的比賽（lineup／bench／plays 任一）」，兩者皆無就不列入該球季的出席率／排行榜，避免顯示「0 場出席」這種誤導性的資料（正確語意是「當時還不在隊上」，不是「缺席」）。出席率的「場數」計算沿用該球季**所有**比賽（聯賽＋盃賽／季後賽都算，出席就是出席，跟聯賽/盃賽分類無關）；但排行榜的打擊數據沿用 `seasonBattingFor()`，跟球員生涯查詢一致只算聯賽成績，不含盃賽／季後賽。**⚠️ Version 19 更新：「場數」對「2025」與「2025-2026聯賽」這兩個封存球季不再是單純數 `games`/`games_final` 文件數量，見下方 Version 19。⚠️ Version 23 更新：每位球員「自己實際出席的場次」對這兩個封存球季，原本也只會算到 App 本身記錄的比賽（幾乎沒有），現在會額外加上匯入的歷史出席次數，見下方「歷史球季的出席率資料」條目與 Version 23。**
- **落點分析球種比例（Version 13 新增，取代原本的球種分布原始次數）**：`battedTypeRateRows(typeCounts)` 把 `BATTED_TYPES`（滾地／平飛／高飛／界外）四種原始次數改成百分比呈現——GB%（滾地）／LD%（平飛）／FB%（高飛）／FOUL%（界外），分母為四種類型的總次數（`fmtPct(part,total)`，分母為 0 時顯示「—」）。套用範圍：球員生涯查詢、對手分析兩處（含全部球員/全部對手，以及篩選特定球員/對手背號時）。
- **投手成績（Version 14 新增）**：`PITCHING_COUNT_FIELDS = ["K","BB","R","outs"]`，`computeSeasonPitching(games)` 對每場比賽呼叫既有的 `computePitching(g)`（原本只在已完賽總結畫面用）逐場加總；`seasonPitchingFor(seasonKey, games)` 比照 `seasonBattingFor()` 的球季／生涯篩選邏輯，但**只吃 App 本身記錄的聯賽比賽**——試算表匯入的歷史資料從來沒有逐場投手數據，所以沒有對應的 `*_IMPORT_KEYS`，歷史球季查投手一樣是空的（這是資料來源本身的限制，不是 bug）。盃賽／季後賽的投手數據也不計入（比照打擊數據的規則）。**⚠️ Version 20／22 更新**：試算表其實有 MVP／勝投／登板欄位（先前判斷「試算表沒有逐場投手數據」沒錯，但漏看了試算表其實有「球季彙總」層級的勝投/登板），已新增勝投（W）／出賽（G）統計並把「2025」「2025-2026聯賽」兩個球季的歷史勝投／登板都從試算表補進 `team/season_2025`／`team/season_2025_2026`，細節見下方 Version 20、Version 22（Version 20 當時對「2025-2026聯賽」有所保留，Version 22 已依使用者說明補齊）。**⚠️ Version 40 新增：`g_hist01`（奕郝）／`g_hist02`（零壹通訊）這兩場歷史比賽本身沒有逐球守備紀錄，其投手數據改用單場的 `statOverrides.pitching` 補上（試算表「01」「02」分頁的投手數據，使用者確認可用），見下方 Version 40。**
- **球隊戰績（Version 14 新增）**：`TEAM_RECORD_IMPORT_KEYS = {"2025":"teamrecord_2025", "2025-2026聯賽":"teamrecord_2025_2026"}`——比照 `SEASON_IMPORT_KEYS` 但存的是「球隊」層級的歷史積分/排名資料，不是球員打擊數據。`Store.getTeamRecord(key)` 讀取 `team/<key>` db 文件（結構 `{rows:[{team,points,rank,results:[...]}], updatedAt}`），fallback localStorage `sb_<key>_v1`。`teamRecordFromGames(games, seasonKey, competitionFilter)` 直接從 App 自己記錄的已完賽比賽（`status==='final'`，排除 `oppLogOnly`）依比分算出精確勝/和/敗與逐對手戰績明細（`byOpponent`，含各對手的 W/T/L/RF/RA）；跟打擊數據不同，勝負不受「盃賽/季後賽會拉低生涯打擊平均」那個顧慮影響，所以這裡盃賽／季後賽**可以**用「賽事類別」篩選查看（不像打擊數據那樣完全分開）。`deriveWTLFromResults(results)` 把匯入資料的逐場勝/和/敗序列（陣列）換算成總計 W/T/L。詳細設計理由見下方新增的「球隊戰績資料來源與限制」章節。**⚠️ Version 39 更新**：`盃賽／季後賽打擊成績` 這個子區塊原本只依「賽事類別」篩選不等於「聯賽」就顯示（即使實際 0 場盃賽/季後賽比賽也會跑出一個空表格），已改成同時要求 `competitionGamesCount>0` 才顯示，見下方 Version 39。
- **對手打線改為固定棒次格（Version 15 新增）**：`oppRoster` 原本是「輸入背號＋姓名後點加入」的動態清單，改為固定長度、依棒次排列的陣列，長度由新欄位 `oppBattingSlots`（10 或 11，預設 10）決定；`setOppBattingSlots(n)` 負責調整陣列長度（變大補空白列，變小則砍掉尾端幾列，若被砍掉的列本來有資料會先跳出自訂確認彈窗提醒，見下方 Version 21）。每一列的背號／姓名都可以留白（選填）——不影響既有的 `currentOppBatter()`／`syncOppBatter()`／`pickOppBatter()` 輪替邏輯——這些函式本來就是依 `oppRoster.length` 循環、以陣列 index 對應棒次，留白的列一樣會排入輪替，守備記錄時可以直接手動輸入該打者的背號／備註（原本就有的功能，不受影響）。
- **每球季實際總場次與 60% 有效打席門檻的計算依據（Version 19 新增）**：`SEASON_GAME_COUNTS = {"2025":24, "2025-2026聯賽":24}`——「2025」與「2025-2026聯賽」這兩個封存球季在球隊試算表/積分表上都是固定 24 場的賽制，但這兩季幾乎所有比賽當時都不是用這個 App 逐場記錄的（只匯入了球隊層級的最終戰績，見「球隊戰績資料來源與限制」），所以直接數 `games`/`games_final` 裡標記該球季的文件數量會嚴重低估（例如可能只有 0～2 場）。`totalGamesForScope(seasonFilter, gamesInScope, allGames)` 取代原本單純的 `games.length`：選定的是有固定總數的封存球季（目前是「2025」或「2025-2026聯賽」）時直接回傳該固定值；選「生涯」時則是「兩個封存球季的固定值相加」＋「不在固定值清單裡的球季（目前的「2026聯賽賽季」及未來任何新球季）實際被這個 App 記錄到的場次」，避免封存球季的比賽被重複計算，也確保「生涯」等於所有球季加總。這個 `totalGames` 同時是出席率卡片「場數」分母，以及 Version 18 排行榜 60% 有效打席門檻（`qualifyMinPA = totalGames * 0.6`）的依據，所以這次修正後兩處數字會一起變得正確——例如切到「2025」球季，總場次會顯示 24（而非幾乎是 0），排行榜門檻也會相應變成 24×0.6=14.4 打席，不再形同虛設。之後若「2026聯賽賽季」結束、變成封存球季，若確定該球季最終固定場次，同樣可以在 `SEASON_GAME_COUNTS` 補上對應的固定值。**⚠️ 這個常數／這段邏輯管的是「該球季／生涯總共打了幾場」（分母），跟下面 Version 23 新增的「某位球員自己出席了幾場」（分子，`GP` 欄位／`importedAttendance()`）是兩件不同的事，兩者搭配才能算出正確的個人出席率。**
- **背號重複的已離隊球員與生涯數據分離（Version 20 新增）**：球隊過去有球員離隊後，空出的背號被新球員承接——目前已知兩組：#19（舊：王崇綺，現：鍾嘉文）、#24（舊：曾筱茹，現：謝文隆）。`battingKey(r)`／`mergeBattingLists()` 原本純粹以背號當唯一識別鍵（本隊自己的資料原本沒考慮到「背號會回收再分配給不同人」，跟對手分析那邊「隊名＋背號」複合鍵的處理不一樣），導致舊球員的歷史匯入資料跟新球員的現場紀錄會被誤判成同一人合併——不只數字加總在一起：因為 `mergeBattingLists`／`mergePitchingLists` 都是「先遇到哪筆資料就先用哪筆的姓名」（`if (!row.name && r.name) row.name = r.name`，第一筆非空姓名寫入後不會被後面覆蓋），而呼叫順序永遠是先放 `imported`（匯入的舊資料）再放 `live`（現場紀錄），代表合併後畫面顯示的姓名會被鎖定在**舊球員**身上，也就是現役球員的生涯查詢畫面會顯示成舊球員的名字，但數字是兩人加總——不只是數字錯，連名字都錯。修正方式：在 `team/season_2025`／`team/season_2025_2026` 這兩份 db 文件裡，把舊球員那筆資料的 `number` 欄位加註 `(原)` 後綴（`"19"`→`"19(原)"`、`"24"`→`"24(原)"`），讓 `battingKey()` 天然產生不同的鍵、跟現役同背號球員的資料分開，不需要改動 `battingKey`／`mergeBattingLists` 本身的邏輯。新增 `formerPlayersFromImports()`：掃描 `AppState.seasonStats` 裡所有匯入球季，動態找出 `number` 含 `(原)` 的列，產生「已離隊球員」清單（不寫死姓名/背號，之後任何新的背號重複情況只要比照套用 `(原)` 後綴就會自動被抓到）——供「球員生涯查詢」「投手成績查詢」兩張卡片的下拉選單額外用 `<optgroup label="已離隊（背號重複，資料獨立保留）">` 列出，讓舊球員的歷史數據仍然查得到、只是清楚標示為已離隊，不會跟現役球員混在一起也不會平白消失。`rosterLookup()` 也一併加上對這份清單的 fallback，讓其他地方（例如打席／守備覆寫表格顯示姓名）碰到 `(原)` 背號時也能正確解析姓名。附帶副作用：`rosterForSeason()` 用同一份背號集合判斷「當季在隊上的球員」，`(原)` 後綴同樣讓它不再誤把現役球員（例如鍾嘉文）算成「2025 球季當時就在隊上」——這點目前還沒有反過來核對球隊實際歷史（鍾嘉文/謝文隆實際加入球隊的正確時間點），如果之後發現他們其實在 2025 或 2025-2026 球季就已經用別的背號待過、之後才改成現在這個背號，這裡的「當季在隊上」判斷可能需要額外處理「同一人跨球季換背號」的情況（目前的資料模型還不支援）。
- **歷史球季的出席率資料（Version 23 新增）**：使用者回報「生涯」出席率沒有把「2025」「2025-2026聯賽」這兩個封存球季算進去，查明原因是出席率統計原本完全從 `games`（App 自己記錄的比賽文件）逐場累計每位球員的出席次數，但這兩個封存球季幾乎沒有用 App 逐場記錄（跟上面 `SEASON_GAME_COUNTS` 的情境一樣），所以這兩季、以及因此連帶「生涯」欄位，每位球員的出席次數幾乎都會落到 0 或極低，即使實際上打了很多場。修正方式：把兩個封存球季每位球員實際出席場次匯入到 `team/season_2025`（30 位球員）／`team/season_2025_2026`（25 位球員）兩份 db 文件的 `GP` 欄位（依球員背號對應，只補有資料的球員，其他球員維持原樣、fallback 回「這個 App 有記錄到多少就算多少」）。資料來源：「2025-2026聯賽」用球隊試算表「出席率」分頁（該分頁直接列出每位球員 24 場的出席次數／出席率／打席數，抽查數字跟使用者提供的截圖完全吻合）；「2025」則因為找不到分頁裡有對應的出席次數欄位，改用使用者提供的另一張截圖（同樣是 24 場基準的出席率表格），逐位球員的 PA/AB/H/RBI 數字先跟已經匯入 db 的 `team/season_2025` 打擊資料逐一核對姓名比對無誤（過程中抓出一處背號截圖辨識誤差：陳柏穎誤讀成「12」，比對後更正為「36」），確認截圖來源可信後才把出席次數寫入。新增 `importedAttendance(seasonKey)` 函式：讀取 `SEASON_IMPORT_KEYS[seasonKey]` 對應的匯入資料，回傳「背號→GP」的對照表；`renderAttendanceView()` 在原本逐場統計 App 自己記錄的出席次數之後，會再把選定範圍內每個有匯入資料的封存球季（「生涯」時是全部封存球季一起加，單一球季時只加那一季自己的）疊加進同一個出席次數物件——因為封存球季幾乎沒有 App 自己的比賽文件，這裡是單純相加、不用擔心重複計算。修正後「2025」「2025-2026聯賽」單獨查詢，以及「生涯」（兩者相加）都能正確顯示出席次數／出席率，不再顯示成「無資料」。

### 「2025」與「2025-2026聯賽」球季資料的對應關係（重要，供之後重新匯入或除錯參考）
球隊試算表「2025-2026振宇」裡與本隊球季成績相關的分頁：
- `Career`：試算表自行維護的生涯總表，但比對後發現對約 12 位邊緣/支援球員的數字有點過時（未完全跟上最新資料），所以本 App **沒有直接匯入 Career 分頁**，而是改成用球季分頁的數字在 App 內即時加總算生涯，確保生涯＝所有聯賽球季加總，邏輯一致不會跟單一球季分開看的數字對不上。
- `2025` 分頁：2025年（春季）已結束的賽季，24場，直接匯入為 `season_2025`。
- `2025-2026聯賽攻守成績` ＋ `2026聯賽攻守成績` 兩個分頁：這是「2025-2026聯賽」球季（跨年度切換時分頁重開分成兩段），兩者相加後才是完整數字，已在匯入時合併為 `season_2025_2026`（合併方式：依球員背號/姓名加總各項計數欄位）。
- 交叉驗證：對大部分球員來說 `2025 + (2025-2026聯賽攻守成績 + 2026聯賽攻守成績)` 加總後打席數與 `Career` 分頁完全吻合（抽查如翁敏捷 62+48+6=116=Career）；有 12 位邊緣球員（多為支援/新加入球員如黃奕宸、張瑋泰等）對不上，判斷是 Career 分頁維護較不即時所致。
- **球季交接（Version 12）**：「2025-2026聯賽」已結束，現場目前在打的是新的「2026聯賽賽季」（`SEASON_DEFAULT` 常數，新比賽預設值）。App 內「2025-2026聯賽」與「2026聯賽賽季」都只會併入**明確標記為該球季**的 App 現場紀錄（透過 `season` 欄位比對，不再像 Version 11 以前那樣「凡是 App 記錄的都算當季」）；未標記 `season` 的舊比賽 fallback 算「2025-2026聯賽」（見上方資料模型重點）。「2025」球季則是封存資料，不會再變動。之後若再有新球季（例如「2026-2027聯賽」），只要改 `SEASON_DEFAULT` 常數＋在 `KNOWN_SEASONS` 陣列加入新標籤即可，球季下拉選單、生涯加總都會自動涵蓋，不需要改查詢邏輯。
- 若未來要重新匯入（例如試算表數字更新，或球季結束要開新一季分頁），流程：用 `mcp__Google_Drive__download_file_content`（`exportMimeType: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`）下載試算表→用 `openpyxl` 讀取對應分頁→依上述規則整理成 `{number,name,PA,AB,H,1B,2B,3B,HR,BB,SF,RBI,R:0,K,DP,E}` 陣列→用 `write_db`（`db_op:"set"`）寫入 `team/season_2025` 或 `team/season_2025_2026`（新球季若要匯入試算表資料，需另外在 `SEASON_IMPORT_KEYS` 加上對應的 db key）。

### 球隊戰績資料來源與限制（Version 14 新增，Version 16 更新「2025」的資料完整度，供之後重新匯入或延伸參考）
「球隊戰績」卡片區分兩種資料來源，呈現方式不同，原因如下：
- **本 App 自己記錄的比賽（含目前的「2026聯賽賽季」及未來球季）**：`teamRecordFromGames()` 直接從每場已完賽比賽的比分算出勝/和/敗，並且知道每一場是打誰（`g.opponent`），所以能算出精確的「逐對手戰績明細」表格（對某隊幾勝幾和幾敗、得失分）。
- **「2025-2026聯賽」（試算表）與「2025」（手寫積分表照片）兩個歷史球季**：都只匯入成**球隊層級的彙總**（`team/teamrecord_2025_2026`、`team/teamrecord_2025`），畫面上顯示「球季積分表」（排名／積分／戰績），**沒有逐對手明細**。原因是這兩個資料來源本身都只有「每隊逐場的勝/和/敗」序列，完全沒有記錄「那一場打的是哪一隊」：
  - 試算表的「2025-2026聯賽戰績」分頁：9隊各自的24格勝/敗/和序列＋積分/排名，序列本身沒有對手欄位。
  - 試算表另外還有「01」～「24」逐場比分分頁（原本期待能補上每場對手是誰），但實際檢查後發現只有「01」「02」兩場真的有填資料（振宇五金 vs 奕郝 3:7 負、vs 零壹通訊 9:8 勝），其餘22場全是空白範本——代表球隊在試算表只手動記錄了2場之後就改用這個 App 記分，因此無法用這批分頁補上遺失的逐場對手資訊。**⚠️ Version 40 更新**：這兩場的「打擊」資料當時已經以彙總方式匯入為 `g_hist01`／`g_hist02`（見下方 Version 17），但一直沒有補上這兩場的「投手」數據；使用者確認這兩個分頁（01、02）的投手數據可用，已補進 `statOverrides.pitching`，見下方 Version 40。
  - 「2025」球季（上上季）是使用者提供的手寫「A組積分表」照片：表頭有清楚的計分規則「勝○=2分／和△=1分／敗x=0分」，主體是 12 個「週」欄位、每欄實際各含 2 場比賽（共 24 場，跟試算表那份同樣是 24 場的規模），逐場用 ○／△／x 符號記錄，旁邊還穿插手寫的累計積分紅字可以逐格核對。**Version 14 當時判斷這張表只有最終總積分／排名可用**、逐場序列風險太高沒有匯入；經使用者確認計分規則後（2分/1分/0分）重新逐格核對 9 支球隊 × 24 場＝216 格符號，並用表上的累計紅字＋每隊最終總積分/排名做交叉驗證，9 支球隊的推算總分都跟表上寫的最終積分完全吻合，因此**現在「2025」也有逐場 `results` 序列**了（`teamrecord_2025.json`／db 文件已更新）。這張照片裡的第4隊隊名一開始誤讀為「奕都」，使用者更正後已改為「奕郝」（與「2025-2026聯賽」試算表資料裡的隊名一致，這兩份資料原本就是同一支球隊在不同球季的紀錄）；唯一仍然辨識信心較低的是第5隊隊名（手寫連筆簽名式寫法，暫記為「台中慶紀」），但這只影響隊名顯示，不影響任何一隊自己的逐場序列或積分。
  - 「2025-2026聯賽」則因為分頁本身是清楚的打字資料（非手寫），24格序列同樣可以放心保留並在 App 內用 `deriveWTLFromResults()` 即時算出總計勝/和/敗（振宇五金驗算：12勝3和9敗 = 12×2+3×1+9×0 = 27分，與分頁記載積分一致）。
  - 即使「2025」現在也有逐場序列，**仍然沒有逐對手明細**——原因同上，兩個資料來源都只記錄「這一場（第幾場）」的勝/和/敗，沒有記錄對手是誰，所以還是無法像 App 自己記錄的比賽那樣列出對某隊幾勝幾和幾敗。
- 因此：**只有 App 自己記錄的球季才有「逐對手戰績」表格**；兩個歷史球季都只有「球季積分表」（含逐場推算出的總勝和敗，但不含逐對手明細）。「新一季（2026聯賽賽季）」目前尚未在任何地方登記過往資料，會隨著球隊持續用這個 App 記錄比賽而自然累積。

### 落點圖三種指標與熱區配色（Version 11 新增，Version 13 微調版面，供之後調整參考）
- `fieldDiagramCountsHTML(zoneStats, metric)`：`metric` 為 `freq`（擊球機率，預設）／`avg`（該落點打擊率）／`slg`（該落點長打率）。
- 配色：`heatColor(t)` 依 t∈[0,1] 做藍(低)→黃(中)→紅(高) 線性插值；t 是該格數值相對於**同一張圖裡其他格子**的相對位置（該指標當下所有格子的 min~max 正規化），不是跨圖或跨球員的絕對刻度。
- 「無資料」與「數值為 0」要分開處理：`freq` 的 0 是真實觀察值（該格從未被打到），一樣參與配色（會是最藍）；但 `avg`／`slg` 在該格 AB=0（尚無出手紀錄）時視為「無資料」，顯示灰底與「—」，不會被誤當成「打擊率最低」。
- 每張圖上方有 `zoneMetricToggleHTML(key)` 產生的按鈕列可切換指標，`key` 讓各張圖的選擇互相獨立存在 `AppState.ui.zoneMetric.{us|opp|def}`：`us`＝球員生涯查詢卡片、`opp`＝對手分析卡片、`def`＝紀錄頁面（即時記錄畫面）我方守備時的對方打者參考卡片。
- 圖形本身放大：新增 CSS class `field-svg-lg`（`max-width:480px`，取代原本 320px），只套用在唯讀的分析圖（`fieldDiagramCountsHTML`），記錄新打席時用的互動選點圖（`fieldDiagramHTML`）維持原尺寸不變。
- **內野文字擁擠修正（Version 13）**：內野 5 個扇形（三／游／投／二／一）扇心角較窄，原本把兩行文字（格名＋數值）放在扇形內外半徑的中點（約 r=60），該處弧寬不足以讓相鄰扇形的文字不互相靠在一起甚至視覺重疊。修正做法是把內野文字改放到扇形**外緣**附近（約 `r2-14`，弧寬大很多），並縮小字體（格名 8.5px、數值 9.5px，外野維持原本 11px/13px）、行距也收緊（`dy1=4,dy2=6`，外野維持 `dy1=6,dy2=9`）。外野扇形因為在中點半徑弧寬本來就夠寬，不受影響、維持原樣。

### 表格點表頭排序（Version 40 新增，供之後調整參考）
- `sortStatsTable(th)`（定義在 `$app` 常數旁）：對任何 `<table class="stats sortable">` 通用的點表頭排序——用事件委派（`$app.addEventListener("click", ...)`，只註冊一次，不會被 `render()` 的整頁重繪清掉）偵測 `table.sortable thead th` 的點擊，依該欄在表頭的 index 取出 `tbody` 每列對應 `<td>` 的文字內容排序：第一欄（球員／背號／投手，永遠是名字/文字）用 `localeCompare`；其餘欄位用 `parseFloat`（先用正規表示式去掉非數字字元，相容 `fmt3()` 產生的「.275」這種省略開頭 0 的格式）。同一個表頭再點一次會切換升冪/降冪（`th.dataset.sortDir`），並用 CSS class `sort-asc`/`sort-desc`（`::after` 加 ▲／▼）顯示目前排序狀態；換點別的表頭會清掉其他表頭的排序標示。純 DOM 排序（直接把 `<tr>` 依新順序 `appendChild` 回 `tbody`），不改動任何底層資料，所以下次 `render()` 重繪時排序狀態不會保留（重新整理/切換篩選條件後會回到預設順序，這是刻意的，避免要另外維護一份排序狀態）；表格若是「尚無資料」的 colspan 佔位列（欄數跟表頭不一致）會被偵測到並直接跳過，不會排序出錯。目前套用在「數據分析」頁面三個表格：球隊戰績卡片內的「盃賽／季後賽打擊成績」、球員成績查詢卡片「全部」時顯示的整隊打擊成績表、對手分析卡片的「依對方背號分析」表；其他表格（球員成績查詢單一球員的那一列、投手成績查詢、出席率／排行榜頁面）目前沒有加，之後若要擴大範圍，直接在對應 `<table class="stats">` 加上 `sortable` class 即可，`sortStatsTable` 本身不需要改。

### 免登入版遷移：Supabase＋GitHub Pages（Version 41 新增，供之後維護參考）
使用者反映每次都要用 Claude 帳號登入才能開啟網頁，隊友覺得麻煩，要求評估不需要 Claude 帳號登入的替代方案。討論後選定「外部資料庫（Supabase）＋免費靜態網頁空間（GitHub Pages）」（使用者手邊已有 GitHub 帳號），因為隊友需要即時輸入/編輯資料（不是單純瀏覽），純靜態匯出檔＋localStorage 無法多人同步，必須換成真正的雲端資料庫。

- **雙模式 Store 設計，同一份原始碼同時支援兩種環境**：`Store` 的 db 初始化改成三層 fallback——`window.SUPABASE_URL`／`window.SUPABASE_ANON_KEY` 兩個全域變數皆非空且 `window.supabase.createClient` 存在時，優先用新增的 `createSupabaseDb(url, anonKey)`；否則沿用原本的 `window.claude.use("db")`（跑在 Claude Artifact 上時）；都不可用時 fallback localStorage（不變）。這兩個全域變數以及 Supabase JS SDK 的 CDN `<script>` 標籤，寫在 `<div id="app"></div>` 之後、主程式 `<script>` 之前，用註解清楚標示「部署到 GitHub Pages 前請填入你自己的 Supabase Project URL／anon public key，留空則自動退回本機儲存」。這代表同一份 `softball-scorer.html`（Claude Artifact 上的原始檔）可以原地繼續當 Claude Artifact 使用（兩個全域變數維持空字串，行為完全不變），也可以填入 Supabase 設定後另外包裝成獨立 HTML 部署到 GitHub Pages——兩邊共用同一套功能程式碼，之後修 bug／加功能只需要改一份檔案。
- **`createSupabaseDb()` 實作**：只需要實作 `Store` 已經在用的極簡子集介面——`db.doc(path).get()/.set()/.delete()`、`db.collection(name).orderBy(field,dir).limit(n).get()`（回傳 `{docs:[{id, data()}]}`）——不需要改 `Store` 本身任何一行程式碼。底層對應一張 Postgres 資料表 `kv_store`（`path text primary key`、`collection text`、`data jsonb`、`created_at bigint`，見下方 SQL），`path`（例如 `"games/g_xxx"`、`"team/roster"`）拆出 `/` 前的部分當 `collection` 篩選欄位；`orderBy` 只會被拿來排 `createdAt`，所以直接對應到獨立的 `created_at` 這個真實欄位（不是解析 jsonb 內部欄位），排序/分頁效能較好也比較好寫。
- **建表 SQL**（Supabase SQL Editor 執行一次）：
  ```sql
  create table if not exists kv_store (
    path text primary key,
    collection text not null,
    data jsonb not null,
    created_at bigint,
    updated_at timestamptz not null default now()
  );
  create index if not exists kv_store_collection_idx on kv_store (collection);

  alter table kv_store enable row level security;
  create policy "public read" on kv_store for select using (true);
  create policy "public insert" on kv_store for insert with check (true);
  create policy "public update" on kv_store for update using (true);
  create policy "public delete" on kv_store for delete using (true);
  ```
  這組 RLS 政策等於「任何拿到網址、且知道 anon key 的人都能讀寫全部資料」——因為沒有登入機制，這是免登入方案無法避免的取捨，等同原本 `games` 集合「任何登入隊友可寫」的精神，只是連 `games_final` 的「僅管理員」限制也一起在資料庫層放開了（改用下面的前端密碼防呆補回一部分）。
- **已完賽比賽的「管理員」保護改成前端密碼防呆**：原本 `games_final` 靠 Claude Artifact 的 db capability 權限規則（僅管理員可寫）保護，脫離 Claude 帳號後資料庫層不再區分身份，於是加了 `requireAdmin(actionLabel)`——只有 `window.SUPABASE_URL`／`ANON_KEY` 有設定（代表跑在 Supabase 模式）時才會生效，跑在 Claude Artifact 上（兩者皆空）時 `requireAdmin()` 直接回傳 `true`、完全不受影響。生效時用 `window.prompt()` 問一次 `ADMIN_PASSWORD`（原始碼裡的明文常數，部署前務必自行修改），答對後設定模組層級變數 `adminUnlocked=true`，同一個瀏覽器分頁之後不會再重複詢問（只存在記憶體，重新整理頁面會重置，不會寫進任何儲存空間）；答錯或取消則動作被擋。掛在四個進入點：`openEditGame()`（編輯已完賽紀錄前）、`reopenGame()`（重新開放編輯前）、`deleteFinishedGame()`（刪除前）、`confirmEndGame()`（`wasFinal` 時，即事後修改已完賽比賽的勝投/MVP前）；另外 `persistGame()` 本身也加了一層保底檢查（`AppState.game.status==="final"` 且尚未 `adminUnlocked` 就擋下），防止任何未來新增的編輯路徑漏掛前面四個進入點也不會真的寫穿。原本三處「只有管理員能…」的提示文字（`confirmEndGame`／`reopenGame`／`deleteFinishedGame` 的 `res.ok===false` 分支）改成通用的「儲存失敗，請檢查網路連線」——因為權限判斷已經在呼叫 `Store` 之前就被 `requireAdmin` 擋掉了，`Store` 本身的呼叫理論上不會再因為權限被拒（Supabase RLS 對這個表本身是全開的），`ok:false` 現在幾乎只代表網路/連線問題。畫面上兩處說明文字（已完賽紀錄的編輯/戰績彈窗提示）改成依 `window.SUPABASE_URL` 是否有值動態顯示對應的說法（Supabase 模式講「需要輸入管理密碼」，Claude Artifact 模式維持原本「僅管理員能儲存成功」的說法），避免兩種環境下顯示不符實際機制的文字。
  - **誠實揭露的限制**：這個密碼只是前端 JS 裡的一個提示視窗，原始碼本身（包含密碼明文）對任何打開瀏覽器開發工具的人都可見，是「同隊互相提醒不要誤改」的防呆，不是真正的存取控制；一個懂技術的人可以直接繞過去改資料庫。這個取捨已經在部署指南裡明確告知使用者。
- **兩份對外檔案，一份原始碼**：`/home/claude/softball-scorer.html` 保留原本的 Artifact 片段格式（無 `<!doctype>`/`<html>`/`<head>`/`<body>`，由 Artifact 工具在發布時自動包裝），繼續發布到既有的 Claude Artifact（Version 41 已發布，含這次 Supabase 雙模式與密碼防呆，Supabase 兩個全域變數維持空字串，對現有 Claude 網址使用者完全無影響）。另外產生 `/home/claude/softball-scorer-standalone.html`——把同一份內容包進完整的 `<!doctype html><html><head>...</head><body>...</body></html>` 結構（`<div id="app">` 之前的內容進 `<head>`，之後的內容進 `<body>`），這份才是要上傳到 GitHub Pages 的檔案。之後任何功能異動都只改 `softball-scorer.html` 這一份原始碼，重新跑同一段包裝腳本（讀取 `<div id="app">` 的位置切開頭尾）即可重新產生最新的 standalone 版本，不需要手動同步兩份檔案。
- **測試**：用 Playwright 在 `window.supabase.createClient` 注入一個純記憶體的假 Supabase client（模擬 `select/eq/order/limit/upsert/delete/maybeSingle` 鏈式呼叫），驗證 `createSupabaseDb()` 與 `Store` 整合後：`getRoster`/`saveRoster`、`saveGame`/`listGames`/`loadGame`/`deleteGame`、`moveGame`（live→final 跨集合搬移）皆正確；並驗證 `Store.usingDb()` 在有效 Supabase 設定時回傳 `true`（確認真的走 Supabase 路徑，不是不小心 fallback 回 localStorage）。另外驗證 `requireAdmin()` 三種情境：密碼正確時解鎖、同一分頁內第二次呼叫不再重複詢問；密碼錯誤時擋下且不解鎖；完全沒有 Supabase 設定（等同目前 Claude Artifact 環境）時直接放行、不會跳出任何提示視窗。獨立跑了一次 standalone 檔案的開機（`boot()`）煙霧測試，確認包裝後的完整 HTML 一樣能正常渲染首頁、無 JS 錯誤（唯一的錯誤訊息是測試環境本身刻意擋掉 CDN 網路請求造成的，不影響邏輯）。`node --check` 對抽出的 `<script>` 內容做語法檢查（`softball-scorer.html`／`softball-scorer-standalone.html` 兩份都測過）。
- **後續使用者需要自行完成的部署步驟**（不影響已發布的 Claude Artifact，是新增的「免登入版」路徑）：在 Supabase 建立免費專案並執行上方 SQL、取得 Project URL／anon public key 交給 Claude 填入 standalone 檔案、上傳到 GitHub Pages。之後任何功能更新，Claude 都會同時更新 Claude Artifact（Version 號照樣往上加）與這份 standalone 檔案，使用者只需要把新的 standalone 檔案重新上傳覆蓋 GitHub Pages 上的舊檔即可，Supabase 裡的資料不受影響。
- **既有歷史資料的一次性匯入（GitHub Pages 部署完成後）**：Supabase 是全新的空資料庫，原本存在 Claude Artifact db 裡的歷史資料（球員名單 `team/roster`、兩份歷史球季彙總 `team/season_2025`／`team/season_2025_2026`、兩份球隊戰績 `team/teamrecord_2025`／`team/teamrecord_2025_2026`、`team/state`，以及 10 場 `games_final` 已完賽比賽，含 `g_hist01`／`g_hist02` 兩場歷史彙總與 `g_opp01`～`g_opp08` 八場對手分析彙總）並不會自動出現在新網站上。**沙盒環境對外連線白名單不含 `*.supabase.co`，所以無法直接從這裡把資料寫進 Supabase**；改用「先用 `read_db` 把資料從 Claude Artifact 的 db 讀出來（`out_dir` 存成本機檔案，`games_final` 10 場合計約 227KB），內嵌進一個獨立的 `import_data.html` 匯入工具頁面（同時內建跟部署檔案一樣的 Supabase URL／anon key），交給使用者用自己的瀏覽器（有真正的網路連線）打開執行一次」的做法。頁面邏輯：列出即將匯入的文件清單→使用者勾選確認→逐筆寫入 `kv_store`（`path`／`collection`／`data`／`created_at` 欄位對應方式跟 `createSupabaseDb()` 內部寫入時完全一致，確保跟之後 App 自己寫入的格式相容）→即時顯示每筆成功/失敗的 log 與最終結果。用 upsert 語意（不是單純 insert）所以刻意設計成可以重複執行也不會產生重複資料或報錯（同一 `path` 直接覆蓋成同樣內容）。這個工具是一次性用完即可的，不需要發布成 Artifact，也不需要放進 GitHub Pages 專案裡——使用者本機執行完就完成任務，之後也可以直接刪除這個檔案。
  - **⚠️ 第一版用 supabase-js（`<script src>` 引入 jsdelivr CDN）結果使用者一打開就卡在「讀取中…」動不了**：根因是這個檔案是透過 `SendUserFile` 交付、直接在對話裡點開預覽（不是先存檔再用手機/電腦的瀏覽器開），這種預覽環境本身有外部網域白名單（依系統提示只允許 `cdnjs.cloudflare.com`），jsdelivr 不在允許清單內，於是那個不帶 `async`/`defer` 的 `<script src>` 會卡住 HTML 解析器、永遠等不到載入完成，後面「解析內嵌 JSON＋顯示摘要清單＋掛上按鈕事件」的整段程式碼完全沒有機會執行——連跟 CDN 無關的摘要清單顯示都被一起卡住，使用者體感上就是「整頁沒有任何反應」。**修正**：整個拿掉 supabase-js 這個外部函式庫依賴，改用瀏覽器原生 `fetch()` 直接呼叫 Supabase 的 PostgREST REST API（`POST /rest/v1/kv_store?on_conflict=path`，帶 `apikey`／`Authorization: Bearer <anon key>`／`Prefer: resolution=merge-duplicates,return=minimal` 三個標頭，body 是單筆陣列）達成一樣的 upsert 效果——這個工具從頭到尾不再有任何 `<script src>` 或其他外部資源，摘要清單改成頁面一載入就能立刻同步執行完成，不需要等待任何網路請求；真正的網路呼叫只發生在使用者按下「開始匯入」按鈕之後。用 Playwright 驗證：（a）把所有非 `file://`／非 kv_store REST 的請求全部 `route.abort()`（模擬完全連不到任何外部網域的預覽環境），確認摘要清單依然正確顯示、不再卡住；（b）攔截實際送出的 16 筆 REST 請求，確認網址／HTTP method／`apikey`／`Authorization`／`Prefer` 標頭與 JSON body 內容都正確（含其中一場比賽完整的 87 筆 `plays` 陣列，不是只有摘要）。**教訓**：交付給使用者、預期會在「對話內預覽」而非「獨立瀏覽器分頁／已部署網站」環境開啟的檔案，不能沿用部署檔案（`softball-scorer-standalone.html`）那套「用 jsdelivr CDN 載入 supabase-js」的做法——那份檔案的使用情境是上傳到 GitHub Pages 後用真正的瀏覽器開啟，不受這個預覽白名單限制；凡是透過 `SendUserFile` 直接交付、使用者很可能就地點開預覽的獨立 HTML 工具，都應該優先避免任何外部 `<script src>` 依賴（能用原生 `fetch()` 達成的就不要额外引入函式庫），或至少把不依賴外部資源的部分（例如畫面初始渲染）跟依賴外部資源的部分（例如某個函式庫功能）解耦，避免後者卡住前者。

  2. **根因**：翻出 `db` capability 的官方型別定義（`db.d.ts`）逐字確認，裡面明確寫著：「Delivered snapshots and their `data()` are frozen ... clone a body before editing it for a write.」（送達的 snapshot 與其 `data()` 都是凍結的物件……編輯之後要寫回去之前，要先複製一份）。而這個 App 的 `Store.loadGame()`／`Store.listGames()`／`Store.getRoster()`／`Store.getSeasonStats()`／`Store.getTeamRecord()` 全部都只用 `{id, ...snap.data()}` 這種「淺層展開」把 snapshot 包成一個新物件——這只複製了最外層，`game.plays`（以及裡面每一筆 play 物件、`lineup`、`statOverrides` 等所有巢狀內容）全部**還是同一個被凍結的參照**。在非嚴格模式（這個 App 的 `<script>` 沒有宣告 `"use strict"`）下，對一個凍結物件的屬性賦值**不會丟出任何錯誤，只會靜默失效**——這完美對應使用者看到的現象：`p.code = value` 執行了、沒有跳出任何錯誤，但 `p.code` 讀回來還是舊值；`persistGame()` 存的是同一個 `AppState.game`，其中最外層的 `updatedAt` 是真正新建立、未凍結的屬性（所以真的會更新、存檔也回報成功），但巢狀的 `plays[idx]` 是凍結參照，序列化出去的內容自然跟改之前一模一樣。這個 bug 只影響「透過 `Store.loadGame()`／`listGames()` 等從 `db` 重新讀回來的資料」——換句話說：**已完賽的比賽（`games_final`）幾乎每次都會透過 `openGame()`→`Store.loadGame()` 重新從資料庫讀取**，所以一定會中；正在進行中的比賽如果從開始記錄到結束都沒有離開過同一個瀏覽器分頁（`AppState.game` 一直是 `newGame()` 建立的全新、未凍結物件），就不會踩到——這正好解釋了為什麼使用者具體回報的是「已完賽的」紀錄編不動，而不是所有比賽。也解釋了為什麼所有既有的 Playwright 測試都測不出這個 bug：這些測試執行時 `window.claude` 不存在，`Store` 會 fallback 到 `localStorage`，而 `JSON.parse()` 本來就會產生全新、未凍結的物件，完全不會踩到這個問題——等於這個 bug 的觸發條件（真的透過 `db` capability 讀取）從來沒有被本機測試覆蓋過。
  3. **修正**：`Store` 內所有「從 `db` 讀出資料後回傳給 App」的地方（`getRoster`、`getSeasonStats`、`getTeamRecord`、`listGames`、`loadGame`），一律在回傳前用既有的 `clone()`（`JSON.parse(JSON.stringify(...))`，本來就是這個 App 既有的深層複製寫法）包一層，產生完全獨立、可自由修改的新物件圖，而不是只淺層展開最外層。這樣一來，不管是編輯已完賽的打擊紀錄、覆寫打擊／投手數據、或任何未來會修改到「從 db 讀回來的資料」的功能，都不會再踩到「看起來改了、實際上因為物件被凍結而什麼都沒發生」的坑。同時移除了第 1 點加的暫時診斷訊息（`#editDebugStatus`），保留 Version 26 第 5 點「單純欄位編輯不呼叫 `render()`」與第 1-4 點「捲動位置還原」這兩個改善（雖然它們都不是真正的根因，但仍然是合理、值得保留的使用體驗改進）。
  4. **測試**：新增 `test_r27_frozen_snapshot.py`——這是第一個真正會踩到這個 bug 的測試，因為前面提到既有測試從不透過真正的 `db` capability。做法：用 `page.add_init_script` 在頁面自己的程式碼跑之前，注入一個模擬用的假 `window.claude.use("db")`，其 `.get()` 會像正式環境一樣把回傳的 `data()` 做**真正的深層 `Object.freeze`**（而不是隨便回傳一個普通物件）；`.set()`／`.collection().get()` 等其他行為也一併模擬，讓整條 `Store` 程式碼路徑跟正式環境幾乎一致。用這個假 db 種一場帶 30 筆打席、`status:'final'` 的比賽，透過真正的 `openGame()` 載入，確認載入後的 `AppState.game.plays[8]` 不是凍結物件（驗證修正生效），再透過真正的 `editPlayField(8,'code','SF')` 把某一筆從 FC 改成 SF，驗證：(a) 記憶體內確實變成 SF、(b) 假資料庫裡實際存的內容也確實變成 SF（這正是先前回報「存了但沒真的改」的那個檢查點）、(c) 重新用 `Store.loadGame()` 讀一次也是 SF（確保不是只在同一次 session 裡看起來有效）。額外驗證這個測試本身有意義：暫時把 `loadGame()` 的 `clone()` 拿掉重跑這個新測試，確認會在第一步（`Object.isFrozen` 檢查）就正確失敗，證明測試真的能抓到這個 bug、不是空測試。連同 `test_r15.py`／`test_r18.py`／`test_r20.py`／`test_r21_dialogfix.py`／`test_r23_attendance.py`／`test_r24_pitchercands.py`／`test_r25_ui_requests.py`／`test_r26_scrollfix.py` 全數重跑通過，`node --check` 語法檢查無誤後才發布。

### 測試方式慣例
- 用 Playwright（`/opt/pw-browsers/chromium`，390×844 viewport）開本機檔案 `file:///home/claude/softball-scorer.html` 測試（`Store` 在沒有 `window.claude` db 時會自動 fallback 到 localStorage，方便本機測試不需連正式資料庫；`team/season_2025` 等文件對應 localStorage 的 `sb_season_2025_v1` 等 key）。
- 用 `node --check` 對抽出的 `<script>` 內容做語法檢查。
- HTML 內容斷言優先用 `page.eval_on_selector('#app', 'el => el.innerHTML')`，不要用 `page.content()`——後者會把整個頁面原始碼（含 `<script>` 裡的程式註解文字）都算進去，可能因為某段舊註解剛好提到已移除功能的中文名稱而誤判斷言通過/失敗。
- 用 Playwright 操作會觸發 `render()` 重繪（整個 `#app.innerHTML` 被替換）的表單時，前一次查到的 ElementHandle 在下一次互動前就已經不在 DOM 上了，每次互動前要重新 `query_selector`/`query_selector_all`，不能快取舊的 handle 連續操作，否則會出現「Element is not attached to the DOM」。
- Publish 前一定要先 `action:"read"` 該 artifact 取得最新版本，否則會被拒絕；若該次讀取回應要求「完整讀過已存檔的原始檔」（檔案較大時會存成本機檔案並附上行數），必須用 Read 工具把該檔案從頭到尾讀完（依行數分批讀取皆可），這個版本才算「已檢視過」，重新 publish 才會成功；若第一次 publish 仍被拒絕（提示「已對這個版本被拒絕過的內容原樣重送」），代表視為已檢視的版本判定跟上次不同，要重新呼叫一次 `action:"read"`（哪怕內容看起來一樣）取得新的檢視標記後再 publish 一次。
- **手寫照片的逐場符號表格，若表頭寫明計分規則（例如 勝○=2分/和△=1分/敗x=0分），優先假設逐場資料是可以可靠轉錄的，不要因為字跡潦草就直接放棄**：轉錄時搭配「累計分數」交叉驗證非常有效——很多手寫表格會在逐場符號旁邊順手記錄累計總分（紅字），把轉錄出的符號逐格換算累計分數、跟表上的累計紅字比對，再跟每隊最終總分/排名核對，只要每一步都對得上，就能大幅提高轉錄信心；反之只要有一步對不上，就是抓到轉錄錯誤的訊號，可以回頭重新檢查該處的符號。
- **隊名等專有名詞，即使數字/符號轉錄已交叉驗證無誤，仍應視為獨立的辨識風險**：手寫或連筆簽名式的隊名／人名辨識信心通常遠低於格子裡的○／△／x 符號或數字，交上成果後仍要留意使用者的更正（例如本輪「奕都」→「奕郝」），發現有其他球季/來源用到同一支球隊時，也要記得用同一個正確拼法，避免同一支球隊在不同資料來源裡出現兩種名字。
- **`db` 裡實際的比賽文件要定期抽查有沒有缺 `season`／`competitionType` 欄位**：這兩個欄位缺漏時的 fallback（見上方「比賽的球季與賽事類別」）本意是兜住 Version 12 上線前的舊資料，但任何原因造成的缺欄位（手動寫 db、匯入腳本漏設、UI 有 edge case 繞過設定流程等）都會被同一個 fallback 靜默套用，可能把「其實是當季」的比賽誤歸類到「2025-2026聯賽」，使用者從畫面上不容易第一時間發現（要主動切换球季篩選才看得出戰績「多了」或「少了」）。遇到使用者回報戰績數字看起來不對時，第一步就該用 `read_db`／`db_op:"list"` 查 `games_final`／`games` 兩個集合裡有沒有缺這兩個欄位的非 `oppLogOnly` 文件。
- **`db` capability 的存取規則（`capabilities.db.rules`）是完整覆蓋式宣告，且不會顯示在 `action:"read"` 讀回來的 HTML 裡**：每次 `publish` 時傳的 `capabilities` 參數若非空，會整個取代先前存的宣告（沒再提到的規則等同撤銷），若省略 `capabilities` 才會沿用先前存檔的宣告——這代表規則一旦被某次 publish 不小心設錯（或設對但後來某次改版忘了再帶上、被意外清空／覆蓋成錯的），會一直沿用下去，且無法單靠讀取 artifact 本身的 HTML 內容察覺（規則存在 artifact 的 metadata，不在頁面原始碼裡）。遇到使用者回報「明明應該任何人都能寫的資料寫不進去／讀不到」時，可以用 `read_db`／`write_db` 搭配 `as_level:"interact"`（模擬一般登入使用者、而非本人的 owner 權限）逐一比對各集合的讀寫結果，找出被誤鎖的集合；確認後在下一次 `publish` 明確帶上完整、正確的 `capabilities.db.rules` 覆蓋掉錯誤的規則即可，不需要改任何程式碼。
- **使用者回報「點了按鈕完全沒反應」（不是看到錯誤訊息，是什麼都沒發生）時，優先懷疑原生 `confirm()`／`alert()`／`prompt()` 被沙盒 iframe 吃掉**：已發布的 Artifact 頁面跑在 claude.ai 的沙盒 iframe 裡，沒有 `allow-modals` 時這三個原生對話框函式會被靜默吃掉、直接回傳 `false`／`undefined`／`null`，完全不會跳出任何畫面。任何 `if (!confirm(...)) return;` 這種寫法在這個環境下都會變成「靜默什麼都不做」，使用者體感上跟按鈕根本沒接上事件監聽器一樣，但本機用 Playwright 開 `file://` 測試時因為（a）不是跑在沙盒 iframe 裡、（b）測試常會用 `page.on("dialog", ...)` 自動接受對話框，兩個因素都會讓這個問題完全測不出來、看起來一切正常。這個 App 已經把所有原生對話框呼叫換成 `appConfirm()`／`appAlert()`（見 Version 21），**之後新增的任何功能都不能再用原生 `confirm`／`alert`／`prompt`**，一律要用這兩個自訂函式；回歸測試也要比照 `test_r21_dialogfix.py` 的做法，用 `page.add_init_script` 明確把原生對話框函式覆寫成直接回傳失敗值，而不是只用 `page.on("dialog", ...)` 自動接受，才能真正測出這類問題。
- **使用者回報「生涯統計沒有算到某個封存球季」時，優先檢查該統計是不是只從 `games`／`games_final` 逐場累計，而封存球季幾乎沒有對應的比賽文件**：這個 App 有好幾類統計（球隊戰績、投手成績、出席率⋯）預設都是逐場從 App 自己記錄的比賽文件累計，但「2025」「2025-2026聯賽」這兩個封存球季當時幾乎都不是用這個 App 逐場記錄的，只匯入了球季/球隊層級的彙總數據（`team/season_2025`、`team/season_2025_2026`、`team/teamrecord_*`）。凡是新增一項「逐場累計」性質的統計，都要記得額外檢查這兩個封存球季是否需要對應的匯入欄位／`importedXxx()` 疊加邏輯（比照 Version 19 的 `SEASON_GAME_COUNTS`、Version 20/22 的 `W`/`G`、Version 23 的 `GP`），不能只靠 App 本身的比賽文件，否則封存球季（以及因此連帶的「生涯」）該項數據會顯示成 0 或嚴重低估。
- **使用者回報「編輯／儲存好像沒生效」時，不要跳過「權限被擋」以外的可能性，尤其是使用者已經明確排除帳號/權限原因時**：這個 App 過去確實有 `games_final` 需要 admin 才能寫入的真實設計（見上方 `db` capability 存取規則），容易讓人先入為主覺得任何「編輯已完賽紀錄失敗」都是這個規則在擋。但 Version 26/27 的教訓是：使用者的說法（「我自己就是要編輯的人」「我就是用現在這個帳號」「就真的改了資料庫沒跟著改」）是很直接的訊號，一旦使用者明確排除某個假設，就不該只是換句話術重複同一個解釋，而要認真找別的根因，也不能停在「UI 層有一個講得通的解釋」就滿足——`render()` 整頁重建造成的捲動歸零、單一欄位編輯不必要的重繪，這兩個都是真實存在、值得修的問題，但都不是使用者真正卡住的根因，只是恰好都能解釋「感覺畫面沒反應」的一部分症狀。**真正的根因要靠實際比對資料庫內容前後差異才挖出來**：`read_db` 逐欄位比對使用者編輯前後的整份文件，發現「存檔動作發生了，但除了 `updatedAt` 以外什麼都沒變」，這種「寫入成功、內容卻是舊的」的訊號，比任何 UI 層的推測都更接近真相——這時應該懷疑「送去存的那個物件，資料本身可能沒有真的被改到」，而不是繼續在 UI／時機／捲動這類表面症狀上打轉。最後靠著在畫面上加一行直接讀取 `document.getElementById` 寫入、完全不經過 `render()` 的暫時診斷文字（請使用者截圖回報實際收到的參數與賦值後讀回的值），才直接看到「賦值那行執行了、但讀回來還是舊值」這個不合常理的現象，逼著去查 `db` capability 的官方型別定義，才發現「snapshot 與其 `data()` 是凍結物件」這個明確寫在文件裡、但先前一直沒注意到的規則——`Store` 只做了 `{id, ...snap.data()}` 這種淺層展開，巢狀的 `plays`／`lineup`／`statOverrides` 全部還是凍結參照，非嚴格模式下賦值靜默失效。**教訓**：(a) 遇到「畫面沒反應/沒更新」類回報，資料庫前後 diff 永遠該是第一步，比任何 UI 層假設都更快排除大量錯誤方向；(b) 當一個修正「講得通、也真的修了某個問題」卻沒有解決使用者實際回報的症狀時，不代表方向錯了要整個推翻，但一定要老實承認「這還沒解決」並繼續往下查，不能因為已經有一個合理故事就停手；(c) 任何直接對「從 `db` capability 讀回來的物件」做屬性賦值的地方，都要先確認這份資料有沒有經過真正的深層複製（這個 App 統一用既有的 `clone()`）——包括這次修的 `getRoster`／`getSeasonStats`／`getTeamRecord`／`listGames`／`loadGame`，以後新增任何從 `db` 讀資料的函式都要照做，不能只淺層展開最外層就直接回傳；(d) 這個 bug 完全沒有被既有的 Playwright 測試抓到，因為所有測試都在沒有 `window.claude` 的環境下跑、`Store` 全部 fallback 到 `localStorage`（`JSON.parse()` 天生就是全新可變物件，不會踩到凍結問題）——`test_r27_frozen_snapshot.py` 特別用 `page.add_init_script` 模擬一個會真正 `Object.freeze` 回傳資料的假 `db` capability，是目前唯一會真正跑到「透過 db capability 讀寫」這條路徑的測試，之後任何懷疑跟 `db` capability 讀寫行為有關的 bug，都應該比照這個做法寫測試，而不能只靠 localStorage fallback 路徑的測試就宣稱「測試都過了」。
- **這個 App 現在有兩種部署形態（Version 41 起）：Claude Artifact（原本的 `softball-scorer.html` 片段，靠 `window.claude.use("db")`）與獨立 standalone HTML（`softball-scorer-standalone.html`，靠 Supabase，供 GitHub Pages 等免登入環境用）——兩者共用同一套 `Store`／功能程式碼，差異只在 `Store` 初始化時選到哪一層 db 實作**：之後任何新功能／修正，都只需要改 `softball-scorer.html` 這一份原始碼一次；只要沒有動到 `Store` 的 db 初始化那一段判斷邏輯本身，兩種部署形態會自動維持行為一致，不需要分別測試兩份檔案的業務邏輯——但每次改完仍建議重新跑一次 standalone 版本的開機煙霧測試（確認包裝腳本沒有壞、`<div id="app">` 切分點沒有跟著程式碼變動而位移），並在真的要交付新的 standalone 檔案給使用者部署前，記得把使用者自己填入的 Supabase URL／anon key／自訂管理密碼這三個值套用進去，不要漏帶或用空字串蓋掉。
